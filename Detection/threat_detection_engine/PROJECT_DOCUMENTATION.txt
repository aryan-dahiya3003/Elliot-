1. WHAT IS THIS PROJECT?
------------------------------------------------------------------------------
A mini SIEM-style detection engine written in Python. It reads NORMALIZED logs
(produced by the log collector/normalizer built by a friend), checks every
event against detection rules written in YAML (the "rulebook"), and when a rule
fires it raises an ALERT through an alert system that is built into the engine.

Pipeline:

  12 log sources --> Collector + Normalizer --> normalized JSONL logs
        (friend's system)                              |
                                                        v
                               [ loader.py ]  clean fields, parse time
                                                        |
                                                        v
                               [ detector.py ] evaluate events vs YAML rules
                                    ^                   |
                                    |                   v
                             [ rules.py ]        [ alerts.py ] dedupe, filter,
                             loads/validates       print to console + save
                             rules/*.yml           alerts.jsonl

The 12 supported log types (value of the "log_type" field):
  firewall, dns, dhcp, linux, windows, authentication, web_server,
  application, network_flow, ids_ips, file_audit, endpoint_edr
(Names like "IDS/IPS" or "Network Flow" are auto-converted to ids_ips and
network_flow by the loader.)


2. HOW TO RUN
------------------------------------------------------------------------------
ONE COMMAND (recommended) - does everything automatically:

  python run.py                              full pipeline on the sample data
  python run.py --logs my_logs.jsonl         full pipeline on your own logs
  python run.py --logs live.jsonl --follow   full pipeline, then live watching
  (options: --no-color  --skip-tests;  on Linux/macOS use python3 if needed)

  It runs these steps in order and stops with a clear message if one fails:
    1. checks the Python version (3.8+)
    2. installs the requirements if missing (if a normal install is blocked,
       it creates a private .venv folder and uses that automatically)
    3. validates all YAML rules and the config
    4. runs the automated tests (a failing test stops the run)
    5. runs the detection engine (batch, or live with --follow)

Individual commands (what run.py runs for you, if you want them one by one):
  pip install -r requirements.txt            (only needs PyYAML)
  python main.py                             run on built-in sample data
  python main.py --logs my_logs.jsonl        run on your real normalized logs
  python main.py --logs my_logs.jsonl --follow   live mode (like tail -F; shows
                                             only lines added AFTER it starts;
                                             appends to output/alerts.jsonl)
  python main.py --validate-rules            only check the YAML rules
  python main.py --no-color                  plain output (for files/pipes)
  python sample_data/generate_sample.py      regenerate the sample data
  python -m unittest discover -s tests -v    run the automated tests

Requires Python 3.8+.  Tested on Python 3.12.

4. TECHNOLOGIES AND LIBRARIES USED, AND WHY
------------------------------------------------------------------------------
Python 3
  Standard language for security tooling; readable, huge ecosystem, easy for
  a team to extend.

PyYAML (the ONLY third-party library)
  Parses the rulebook and config. YAML was chosen because it is human-readable,
  supports comments, and lets analysts write rules without programming.
  We use yaml.safe_load() (never yaml.load) so a malicious rule file cannot
  execute code.

Python standard library (no install needed):
  json        - logs are JSON Lines; also used to write alerts.
  re          - regular expressions for patterns (SQL injection, DGA, etc.).
  collections - deque (sliding time windows) and defaultdict (per-key state).
  datetime    - timestamp parsing and UTC output.
  argparse    - command-line options.
  functools   - lru_cache so each regex is compiled only once (speed).
  uuid        - short unique alert IDs.
  glob/os     - finding rule and log files.
  time        - polling in follow mode.
  unittest    - tests, so the project needs no extra test library.
  subprocess/venv/sys - used by run.py to run each step and, if needed, create
                a private virtual environment for the requirements.

JSON Lines (.jsonl) format
  One JSON object per line. Easy to append, stream, and read line-by-line
  without loading a huge file in one go.

MITRE ATT&CK
  Every rule has a "mitre" tag (e.g. T1110 = Brute Force) so alerts can be
  mapped to the industry-standard attacker-technique framework.

ANSI colours
  Console output is coloured by severity (cyan/yellow/red/magenta) so the
  important alerts stand out. Disable with --no-color.


5. NORMALIZED LOG FORMAT EXPECTED
------------------------------------------------------------------------------
One JSON object per line. Required: "timestamp" and "log_type". Other common
fields (all optional; use whatever your normalizer provides):

  src_ip, dst_ip, src_port, dst_port, protocol, action, user, host, status,
  event_id, message, process_name, parent_process, command_line, url,
  status_code, user_agent, query, record_type, bytes_out, direction, mac,
  server_ip, file_path, signature, priority, app, level, event, user_role,
  geo_country

Example:
  {"timestamp":"2026-10-04T09:01:40Z","log_type":"firewall",
   "src_ip":"203.0.113.50","dst_port":22,"action":"deny"}

Timestamps may be ISO-8601, epoch seconds/milliseconds/microseconds/nanoseconds
(number or text), Apache "04/Oct/2026:09:01:40 +0000", RFC-2822, or syslog
"Oct  4 09:01:40" (syslog has no year: the current year, UTC, is assumed).
A line that is not a JSON object, or has no readable time, is skipped + counted.

IMPORTANT: if your friend's field names differ, DO NOT edit the Python code.
Add the names under field_aliases in config.yml, or edit field names inside the
rules. A missing field means the rule does not match that event. If the missing
field is one a rule needs for grouping (group_by), the end-of-run summary prints
a NOTE naming the rule and field, so the problem is no longer silent. (Match
rules still fire and show the missing group field as "unknown".)


6. HOW A RULE LOOKS AND WORKS
------------------------------------------------------------------------------
  - id: LNX-001                      unique ID
    name: SSH brute force            title shown in the alert
    severity: high                   low | medium | high | critical
    type: threshold                  match | threshold | distinct_count | sequence
    log_type: linux                  which log source(s) it applies to
    conditions: {message|contains: Failed password}   all must be true (AND)
    group_by: [src_ip]               count separately per source IP
    threshold: 6                     fire at 6 events...
    window: 60                       ...within 60 seconds
    mitre: [T1110]                   ATT&CK technique
    description: ...                 shown in the alert
    recommendation: ...              what the analyst should do

Rule types:
  match           Fires on a SINGLE event (e.g. event_id 1102 log cleared).
  threshold       Fires when N matching events happen within X seconds per
                  group (brute force, scans, ransomware file changes).
  distinct_count  Fires when N DIFFERENT values of a field are seen within X
                  seconds (port scan = many ports; password spray = many users).
  sequence        Fires when steps happen in order within a window for the same
                  group (5 failed logins THEN a success = likely compromise).

Condition operators (written as  field|operator: value):
  eq (default for single value), in (default for a list), ne, nin, contains,
  contains_any, startswith, endswith, regex, gt, gte, lt, lte, exists.
  Text comparison is case-insensitive.

Extra: "any_of" lets you list several alternative condition groups (OR logic);
"enabled: false" disables a rule; dotted names (process.name) read nested JSON;
a value written as  $lists.name  is replaced by the list called "name" under
lists: in config.yml (an unknown name fails with a clear error).

To ADD a rule: copy an existing rule into any .yml file under rules/, change
the fields, run  python main.py --validate-rules.  No code change, no restart
of anything else.

8. ALERT SYSTEM DETAILS
------------------------------------------------------------------------------
Integrated: the detector calls AlertManager.raise_alert() directly - there is
no separate service or message queue.

Each alert contains: alert_id, rule_id, rule_name, severity, description,
mitre list, recommendation, group (e.g. which src_ip), event_time,
evidence_count, and up to 5 raw evidence events.

Features:
  * Severity filter  - config alerts.min_severity.
  * De-duplication   - same rule + same group is reported once per
                       dedupe_seconds (default 120) so one attacker does not
                       flood the screen. Suppressed count shown in summary.
  * Window reset     - after a threshold/distinct alert, its window is cleared.
  * Handlers         - ConsoleHandler (coloured) and JsonFileHandler
                       (output/alerts.jsonl; overwritten in batch mode,
                       appended to in --follow mode). Adding email/Slack/syslog later
                       = write a class with handle(alert) and add it to the
                       handler list in main.py.
  * Summary          - totals per severity and per rule at the end of a run.


9. DESIGN DECISIONS (WHY IT IS BUILT THIS WAY)
------------------------------------------------------------------------------
- Rules in YAML, logic in Python: analysts can change detections without
  programming, and engine code stays small and stable.
- Field aliases: normalizer field names vary; this avoids code changes.
- Streaming design (process one event at a time): the same detector works for
  batch files and live tailing; memory use is bounded by the sliding windows.
- Event time, not wall-clock time: windows use the log's own timestamp, so
  replaying old logs gives the same result as live running.
- Validation at load time: a typo in a rule fails immediately with a clear
  message instead of silently never firing.
- Only one dependency: easy to install and audit.

11. LIMITATIONS AND HONEST NOTES
------------------------------------------------------------------------------
- State is in memory: restarting live mode forgets the open windows (idle
  windows are also dropped automatically while running, so memory stays bounded).
- Single process, single thread; fine for thousands of events/second at most,
  not enterprise scale. For large volume use a stream platform (Kafka etc.).
- Live mode follows ONE file (not a folder). It handles rotation/truncation, but
  lines written while the engine was not running are not read.
- Field names in rules (e.g. status, event_id, geo_country) are ASSUMPTIONS
  about the normalized schema. They must be checked against the real output
  of the friend's normalizer.
- Environment-specific values must be edited in config.yml under lists: (DHCP
  approved servers, allowed countries, bad domains). Thresholds inside the rule
  files (FLOW, FW, AUTH ...) still need tuning on real traffic to reduce false
  positives.
- Rules detect known patterns; they do not do machine-learning anomaly
  detection or threat-intel feed lookups.
- Alerts are not yet sent to email/Slack and there is no web dashboard.

13. QUESTIONS PEOPLE MAY ASK
------------------------------------------------------------------------------
Q: Why YAML and not hard-coded Python rules?
A: Readability, easy editing by non-programmers, version control friendly.

Q: How is this different from a SIEM like Splunk/Wazuh?
A: Same core idea (rules over normalized logs), but this is small, readable and
   built for learning/customization; it lacks their scale, UI and integrations.

Q: What happens if a log line is corrupt?
A: It is skipped and counted ("unreadable lines skipped"); the run continues.
   This covers broken JSON, lines that are not JSON objects, and lines whose
   timestamp cannot be understood. A wrong file path gives a clear error message.

Q: Why do some alerts not appear even though attacks happened?
A: Possibly de-duplication, min_severity filter, a field name mismatch with
   your normalizer (check field_aliases and the NOTE printed at the end of the
   run), or the threshold not reached.

Q: How do I test a new rule?
A: Add it, run --validate-rules, then feed it a small JSONL file containing the
   attack events. Add a case to tests/test_engine.py.

Q: Does it work in real time?
A: Yes, with --follow it tails a log file and alerts as lines arrive.

Q: Where do alerts go?
A: Screen (coloured) and output/alerts.jsonl.

Q: How does the sequence rule work?
A: Per group it tracks progress through the steps; if the window expires the
   progress resets; when the last step matches, it alerts.

Q: Is it safe to load rules from YAML?
A: Yes, safe_load is used, so rule files cannot run code.
